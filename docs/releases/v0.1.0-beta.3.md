# ProcLens 0.1.0-beta.3

Third public beta. ProcLens shows what Windows Task Manager leaves out: where all your memory
goes, which programs and files are really hitting the disk, and how much CPU your drivers use.

**This is a beta, and it has been tested on exactly one PC** (Windows 10 Home 22H2, build
19045.7725, x64). Please read "Before you run it".

## What's new since 0.1.0-beta.2

No new views. This release is a code review of the part that matters most for an elevated program:
the collector, the named pipe it shares with the window, and the messages that cross it. Ten issues
were found; nine are fixed and one is documented rather than changed.

- **Broken or oversized messages can no longer wedge the link.** A message announcing more than 16 MB
  used to leave the connection reading garbage; it now closes the connection. A program on the other
  end that stops halfway through a message is dropped after 5 seconds instead of tying up a thread
  (and, for the collector, keeping it from exiting). The collector accepts at most 16 connections at a
  time. The window also gives the collector 5 seconds to answer its hello.
- **Standard users who approve the prompt with an administrator's password can connect.** The collector
  then runs under the administrator's account, and the pipe used to admit only that account, locking
  the window out. The window now passes its own account to the collector it starts and the pipe admits
  both. (Unit-tested and the pipe's access list was inspected live; I could not test it with a second
  Windows account.)
- **`PROCLENS_COLLECTOR` is ignored in release builds.** That variable chose which program the window
  elevates and trusts, so anything running as you could have set it. It still works in debug builds.
  If you relied on it, say so in an issue.
- **File names: fewer "not identified" bytes under load.** A timer tick that landed while a file's name
  was being looked up could report that file's traffic as unidentified and throw the name away.
  Fixed, with tests.
- **A hung handle lookup is bounded.** Looking up a name from the system handle table runs on a
  worker with a timeout; if it hung, the worker and the handle it had duplicated stayed behind without
  limit. A hung lookup is now cancelled; if it still does not return it is abandoned, it closes its own
  handle if it ever returns, and at most 8 can be abandoned at once (further lookups are skipped, so
  those files show as "not identified", until some return). I could not make a lookup hang on this PC,
  so this is tested with a stand-in that never returns. (A first version terminated the stuck thread;
  that crashed the test process about 1 run in 30, so it was dropped before release.)
- **The elevated self-tests no longer use a guessable temp file.** `collector.exe` writes test files
  to your temp folder while elevated; they now get unpredictable names and are created only if the name
  is free, so a file or link planted there is never opened.
- **"Check for updates" no longer offers a beta to someone on a stable release.** No stable release
  exists yet, so you will not see a difference until one does.
- Smaller fixes: the memory page-list privilege is requested once instead of per sample, a token handle
  no longer leaks on an error path, the event counters no longer take a lock for every kernel event,
  two garbled documentation comments are repaired, and `collector.exe` with no arguments now lists
  `profile` and `discover`.
- **Documented, not changed:** any other program running as *you* can still connect to the collector,
  read what it reports and ask it to stop. See "Security notes" in the README. The collector is
  read-only, so it cannot change anything.

Verification on the one tested PC: all unit tests pass, the pipe was exercised live (malformed request,
oversized message, half a message, the connection cap, shutdown) and an elevated end-to-end run
started the collector the way the window does, passed all 8 self-tests and accounted for a 64 MiB read
and write workload.

## Before you run it

- **One tested machine.** Windows 11, other Windows 10 builds, other editions and other hardware are
  untested. On a build it doesn't know, ProcLens says so ("Untested Windows build"), labels its event
  tables as a best guess, and runs built-in self-tests whose results appear on the **This PC** tab; a view whose
  check failed also shows a warning. (Only the memory breakdown turns itself off automatically; the
  other views keep running.) You may still see wrong or missing numbers. If you do, that is exactly the feedback this beta is for.
- **It needs administrator approval.** The window itself runs as a normal user. Reading kernel-level data
  needs a separate small helper, `collector.exe`, which the app starts through the usual Windows approval
  prompt each time. The helper only reports data; it cannot end, change or inject into other programs. Click
  **Stop collector** to end it; if the app goes away without that, it exits by itself after about 30
  seconds. (Closing the window is meant to stop it too, but that path has not been tested.)
- **Where you unzip it matters.** The app starts `collector.exe` from its own folder with administrator
  rights. If that folder is writable by ordinary programs, anything running as you could swap in a
  different `collector.exe` and have it elevated when you approve the prompt. For real protection put the
  folder somewhere only administrators can write, such as `C:\Program Files\ProcLens`.
- **The files are unsigned.** Windows SmartScreen will warn about them, and security software may object
  to a tool that enables debug privilege and reads the system handle table. The development PC has
  Bitdefender installed and the locally built copies ran without being blocked; I can't see its logs, and
  I have not scanned the downloadable zip.
- **Needs the Microsoft Edge WebView2 runtime**, which is normally already installed.

## Install

**Installer (recommended).** Download `proclens-0.1.0-beta.3-windows-x64-setup.exe`, check its SHA-256
against the value below, and run it. It asks for administrator approval and installs to
`C:\Program Files\ProcLens` (all users; there is no per-user option, for the reason given above), adds a
ProcLens folder to the Start menu (and a desktop shortcut, ticked by default; untick it to skip) and an uninstaller
under Apps & features. Then start ProcLens, click **Start collector**, and approve the prompt. The setup
file is unsigned, so SmartScreen will warn about it too.

**Portable zip.** Download `proclens-0.1.0-beta.3-windows-x64.zip`, check its SHA-256, extract it (see
the note above about where), run `proclens-app.exe`, click **Start collector**, approve the prompt.

## What it does

- **Memory:** every byte of RAM split into in use, modified, standby cache and free, with where the "in
  use" part sits.
- **Disk & files:** per-process physical disk traffic and file requests, disk response time, and the
  busiest files. The trace runs only while this tab (or Drivers) is open.
- **Drivers:** CPU time each driver spends handling hardware interrupts, which Task Manager folds into
  "System".
- **This PC:** your exact Windows build, whether it has been verified, and the result of each live
  self-test.
- **Command line:** `collector.exe profile` (build and self-tests), `collector.exe discover` (run
  elevated: works out this build's event tables from the live system and compares them with the
  profile), plus `mem`, `procs` and `etw` dumps.

## Known limitations

- Driver CPU times are estimates: on the tested PC they landed within roughly 14-27% of Windows' own
  counters for DPC time and within about 27% for interrupt time. Disk response time is converted with the
  machine's performance-counter rate and looked plausible on SSDs, but was not checked against an
  independent timer.
- Some file traffic cannot be tied to a file name (files opened before tracing that no longer have a
  readable handle): 8-9% in earlier testing, under 1% in the last run after the fix above. Expect it to
  vary with what your PC is doing.
- Some of what ProcLens reads (the memory page lists, the system handle table, one interrupt event type)
  is undocumented by Microsoft and can change in a Windows update. Each is guarded by a runtime check,
  but a future update could still make those checks fail. `docs/REFERENCES.md` lists exactly which
  documentation covers what.
- No auto-update, no code signing, no history (nothing is recorded when the app is closed). With the
  app open, setup and the uninstaller ask you to close it (both tested). If the collector is still running when you uninstall or upgrade, Windows may ask
  to close it or defer removing `collector.exe` to the next restart; click **Stop collector** first.
- A file handle that is closed and reused between the moment the handle table is read and the lookup
  can give one file the wrong name. It is a wrong label for that file only.
- Uninstall leftovers: on the one PC tested, after an uninstall an empty `C:\Program Files\ProcLens`
  folder and the WebView2 cache folder `%LOCALAPPDATA%\uk.aity.proclens` were still present (the
  uninstall log reported removing everything; I did not find out why). They are safe to delete by hand.
- The `discover` command's calibration thresholds were tuned on one machine.
- Licensing: `THIRD-PARTY-NOTICES.txt` lists the 255 Rust crates and 4 JavaScript packages in the
  binaries with their licence identifiers, followed by the full licence texts shipped in each package
  (157 distinct texts, grouped so identical ones appear once). Six crates ship no licence file in their
  archive; for those the text comes from the upstream repository (or, for `selectors`, the standard
  MPL-2.0 text, since its repository has none), as recorded in `docs/licenses/README.md`. Five
  unmodified crates are MPL-2.0 (cssparser, cssparser-macros, dtoa-short, option-ext, selectors); their
  source is at the repositories named in that file.

## Feedback

Open an issue at https://github.com/anubisalpha/proclens/issues. The most useful thing you can attach
is the output of `collector.exe profile`, and, on a Windows build other than 19045, an elevated
`collector.exe discover`. `profile` shows your Windows build and patch level, whether it matches a
verified profile, the result of each self-test, and the quirks recorded for that profile, and it also
describes the machine the profile was verified on (not yours). `discover` prints event types and field
names only. With the installer, run them from `C:\Program Files\ProcLens`; see the README.

Everything in this release was built from the tagged commit with `tools/package-release.ps1`.
